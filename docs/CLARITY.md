# Clarity and rules tooltips

The plan for four clarity iterations ("less text on screen, tooltips instead of long descriptions") and the colour-coded rules tooltip pass ("rule cards like D&D Beyond or Roll20 on spells, conditions, monsters, items and rules, across every module and the books"). Built from an audit of every text surface as DM and players on desktop, iPad, phone and the TV display, and research on D&D Beyond, Roll20, Foundry and Owlbear. Each iteration ships as its own version; the version number is assigned when it merges.

## Principles

1. Plain words. Say the thing the way the DM says it at the table: 'Locked', 'Hidden', 'DC 15 Dex'. Internal vocabulary ('hidden object · hidden from players', 'dm-note', 'X21-lower') never reaches the screen. Where an internal term is needed, it goes in a tip.
2. One idea per line. A line does one job: a name, a state, a check or an action. A sentence over 25 words is split, and the second half goes behind 'More' or into a tip.
3. Show what is essential and put the rest one step away. The first view of every surface carries only what is needed to act now: name, state, actions and the first sentence. Everything else stays on the same surface and is never moved to another sheet.
4. No information is lost on any device. Every string shown today stays reachable in one tap on touch (iPad first) or one hover or focus on desktop. Information never lives only in the tip of an action button: a tip on an action button repeats its name and shortcut only. Moved information sits in a toggletip button, a visible caption, a 'More' disclosure, or a list (Help 'Recent messages', Rooms 'Notes on this level'). e2e/tooltips.spec.ts collects today's strings per surface and proves each one is still reachable by a tap on the touch projects and a hover on desktop.
5. Icons always come with words. Every icon button has a name (aria-label plus data-tip). Every coloured chip also carries a glyph and, inside its card, the type word, so colour, icon and word never have to work alone. That covers colour blindness, both UI themes and the gothic and pastoral backdrops. No two buttons with different jobs share an icon.
6. One visual language per kind of thing. Each lookup() kind (spell, condition, monster, creature type, item, rule, action, damage type, dice, ability, skill, check), plus person, area and DM-only text, maps to exactly one colour token, one glyph and one type word through an exhaustive switch in ui/kinds.ts. Neutral --ink-2 is used for edition and rarity badges, never a kind colour.
7. DM-only text never travels into a tip on the players' side. Every tip and card is built from typed sources tagged 'player' or 'dm'. One function drops the 'dm' sources whenever app.restricted is true or mode is 'player', before any HTML is built. The tooltip manager also closes and rebuilds everything when the view or restricted state flips. The Player Display mounts no tooltip manager at all.
8. Presentation only. The pass changes how text is laid out, shortened, coloured and disclosed. Taps, picks, reveals, movement, travel arithmetic, measurement, camera zoom and scene nesting do not change. No gesture gains a second meaning: map long-press stays reserved for the increment 6 ping hold, and a press on an icon button fires on release exactly as today. Approved APPROVALS items are built by their own versions, not here. A10 (moving descriptions to the area panel) stays declined: text is collapsed in place in the same menu.
9. Every change is measured. Each surface has a word budget whose parts sum to its cap, counted by one countVisibleWords(el) helper. Contrast is asserted on opaque surfaces. Touch reachability is asserted by tap on the iPad and phone projects. Every rules auto-link appears in a review list, and link quality is scored for precision and recall against a committed gold fixture.
10. Scene data stays generated. scene.json, world.json and the manifests are not edited by hand. Every link decision lives in app/src/books/term-overrides.json. If authored tags are ever wanted, they go into scripts/authoring/*.py behind the golden diff (PITFALLS #28).

## The shared tooltip component

One shared component, built in new files app/src/ui/tooltip.ts (manager, placement, event routing), app/src/ui/rulecard.ts (rich card renderer), app/src/ui/kinds.ts (kind to colour token, glyph and type word) and app/src/ui/text.ts (esc, firstSentence, clampWords). It replaces every title= attribute (22 in main.ts; 2 in worldmap.ts; 1 each in bestiary, encounter and minimap) and the ad-hoc .tip in main.ts.

THREE TRIGGER FORMS (the touch rule).
1. Action button (button.icon and any button that does something). Its data-tip holds only its name and, where bound, its shortcut. It never holds information that is not also visible or reachable elsewhere. Mouse or pen hover shows it after 500 ms; :focus-visible shows it at once. On touch, a press held 500 ms or more shows the tip while the finger stays down, and release fires the button exactly as today (sliding off cancels, as today). A short tap fires as today with no tip.
2. Toggletip. Any element that carries information in data-tip and is not itself an action button is rendered as <button type=button class="tt" aria-expanded aria-controls>: 32 px tall with a 44 px hit box. A tap or click opens its tip pinned. A second tap, an outside tap, the X or Esc closes it. Mouse hover also previews it. Keyboard: Tab, Enter or Space. This covers state chips, token stat chips, the top-bar 'p.216' and '5 ft' chips, the Section readout, the measure result chip, the (i) glyphs on sheet headers, Rooms, Library and world Places rows (a trailing (i)), the clock's 'Advance' breakdown, travel detail, the DM subtitle on object cards and the turn-bar chips on the DM phone bar.
3. Term chip (rules). <button class="term" data-kind data-term aria-expanded aria-controls> opens a tier-B rule card (below).
Not tooltips at all:
- Native <select> options (iOS shows a native picker and ignores option titles). The selected option's detail is a visible one-line caption under the select ('3 mph · 24 mi/day', 'Floor 2 · +12 ft · party here').
- Toasts. .status keeps pointer-events:none. The long form shows the first time a message occurs in a session, and the last 10 long forms are listed in Help under 'Recent messages'.

EVENT ROUTING BY pointerType, NOT MEDIA QUERY.
- pointerType 'mouse' or 'pen': pointerenter starts the hover-intent timers.
- pointerType 'touch': a tap toggles the tip or card pinned. The click that follows a touch pointerdown never runs hover logic, so an iPad with a trackpad or a touchscreen laptop cannot open and immediately close a card.
- @media (hover:hover) is used only to scope :hover CSS styling.
- Keyboard hints (kbd chips such as [R], and any 'Esc' wording) appear once a keydown has been seen in the session, whatever the pointer.

EXCLUDED FROM THE LONG-PRESS TIP: every press-and-hold or capture control, enumerated from the code: .vs-peek (hold to peek, pointer capture), the view-slider track (drag with pointer capture), the canvas (installPointer brush capture and OrbitControls), the world-map SVG (pan and party drag with capture), the minimap canvas (tap to look), every <input type=range> (Section, clock time, grid opacity), the A1 'hold 1 s to leave Players mode' control (0.2.1), the increment 6 Pointer tool ping hold, and any element with data-hold. tooltip.ts builds this list as one exported selector, and a unit test fails if a new setPointerCapture call site is not on it.

NO MAP LONG-PRESS. The canvas gets no new gesture. docs/UPGRADES.md reserves long-press on the map for the increment 6 ping hold. Touch users get hover parity this way: the card a tap opens repeats describe()'s title and subline in its header; the DM Rooms sheet gains 'Notes on this level' with the full text of every note and object label; and once increment 3 (0.4.0) makes DM labels open their card, a label tap opens it in one tap.

TIER A, PLAIN TIP. A title line (14px/600, 6 words or fewer, verb first for buttons) with an optional shortcut in a kbd chip, plus an optional second line (13px, --ink-2, 12 words or fewer). Hover tips use role=tooltip with aria-describedby. Pinned toggletips use a live region and stay open until dismissed. Max width 260px. pointer-events:none only for hover tips; pinned toggletips accept taps.

Shortcut chips come from one KEYMAP table (app/src/core/keys.ts, the table increment 3 introduces; created here if clarity-1 lands first), read by both the keydown handlers in main.ts and viewSlider.ts and by the tips. The keys bound today are: '/', r, R, f, n, [, ], \ and Escape. tests/keys.test.ts asserts every shortcut shown in a tip is bound. 'Whole building' has no shortcut, so its tip shows none.

TIER B, RULE CARD (D&D Beyond style). Width min(320px, 100vw - 24px). It sits on the opaque surface token --card (#ffffff light, #232325 dark) with a 1px hairline, a shadow and a 4px header strip in the kind colour. It never uses the translucent --panel. From top to bottom:
(1) Header: kind glyph (18px, kind colour), name (16px/600), and a 'DM' badge with the eyeOff glyph when any line comes from a 'dm' source.
(2) Type line (13px, italic, kind colour), for example 'Level 3 evocation spell', 'Condition', 'Medium undead · CR 1', 'Wondrous item · uncommon · attunement', 'Skill · Wisdom', 'Fire damage'.
(3) Key-stats row, a grid of label and value cells (label 12px caps --ink-2, value 15px/600):
- Spell: casting time, range, components and duration, plus C and R chips.
- Monster: AC, HP, speed and CR, plus a second row of six ability mods.
- Item: rarity as a word plus 1-6 filled pips in --k-item, attunement, cost and weight. No D&D Beyond rarity hues.
- Check: DC, ability, skill and passive.
- Damage and dice: dice, average and max.
- Condition and rule entries have no stats row.
(4) Body: the summary field from lookup(), at most 60 words. Conditions show at most 5 bullets. Nested terms in the body are chips too; opening one replaces the card's content with a back chevron (history up to 5), so cards never stack.
(5) Footer: 'Open in Books ›' (DM side only) and, on the right, the edition badge ('2014 · SRD 5.1' or '2024 · SRD 5.2.1') from the Rules edition preference. When the entry differs between editions there is a 'See 2024' / 'See 2014' toggle that swaps the card in place. When the preferred edition lacks the entry, the card shows the other edition with a neutral --ink-2 badge carrying a ⚠ glyph ('⚠ 2014 only'). A field missing from the lookup result drops its cell; there are no blanks.
Body text is 15px when the last pointerType was touch and 14px otherwise; nothing in either tier is below 12px.

ONE SOURCE PER STAT CARD. A monster card shows lookup(name, edition) for the chosen edition only. bestiary.ts STATS appear only when lookup has no entry, under the label 'Module stats'. The two are never merged field by field.

INLINE TERM CHIP. A 1px pill whose border is the kind colour, background color-mix(in srgb, var(--k) 10%, var(--card)) in light and 16% in dark, and a 0.8em glyph before 13-15px text in the kind colour. Inside running prose the variant is lighter: a dotted 2px underline in the kind colour plus the glyph. Hit box 32px tall through padding or a pseudo-element; 44px wide where the chip stands alone. -webkit-touch-callout:none and user-select:none apply to .term and .tt only. Every surface that holds chips (tap menu, object card, token panel, sheets, world pin card) uses the opaque --card background.

ONE AT A TIME, ONE OUTSIDE HANDLER, ONE ESC STACK.
- The manager holds at most one hover tip, one pinned toggletip and one rule card.
- It replaces the four setTimeout(... addEventListener('pointerdown', ..., {once:true})) calls in main.ts (lines 365, 392, 405, 427) with one persistent document-level pointerdown handler (capture phase), evaluated in this order:
  1. A press inside .rcard, .term or .tt is ignored.
  2. A press outside an open rule card or pinned toggletip closes only that card or tip.
  3. Otherwise the open tap menu or info card closes, exactly as today.
  The existing details.menu handler at line 275 is unchanged.
- Esc stack: if a rule card or pinned tip is open, Esc closes the topmost one and stops there. If none is open, Esc reaches main.ts's handler exactly as today (sheets close, placing stops, selection clears, the tool resets). So a second Esc stops the tool, and with no card open Esc behaves as today.
- Any new surface clears tips and cards: app.onTap, setLevel, opening a sheet, menu or card, the start of a camera drag, and app.onLeave. This fixes the stale 'Party · Tap to pick up and move' tip seen over the 2A menu and after a floor change.
- Rule cards and pinned tips render in a #tips layer above #ui.

VIEW FLIPS. The manager subscribes to app view and restricted changes: the slider dragged to Players, peek held ('\' or the eye), and the mode switch. On any flip it closes every tip and card, and it re-renders the turn bar and any open card through the audience filter.

PLACEMENT, in one placeCard(anchorRect, size) helper (plain JS, no CSS anchor positioning, because iPadOS older than 26 lacks it):
- Prefer below the anchor, then above, right and left, choosing the side with the most room. Flip at the viewport edges with an 8px margin and a 6px arrow.
- The card never intersects its anchor.
- Below 480px viewport width, rule cards dock as a bottom sheet (max 50vh, grab bar and X). If the anchor would fall under the sheet, the owning card or sheet scrolls the chip into view; the canvas is never panned.
- It respects env(safe-area-inset-*) and never sits under the top bar.

DISMISSAL: Esc (per the stack), an outside tap or click, the X, the trigger tapped again, any new surface, and mouse leave plus a 250ms grace with a 50px buffer for hover-opened cards only. Never a timer for pinned ones (WCAG 1.4.13: dismissible, hoverable, persistent).

ACCESSIBILITY: hover tips use role=tooltip with aria-describedby. Toggletips and rule cards use a button with aria-expanded; rule cards are role=dialog (non-modal) with aria-labelledby pointing to the name. On open, '<name>, <type line>' goes into a polite aria-live region. Enter or Space opens; focus moves to the card's first link; Esc returns focus to the trigger. prefers-reduced-motion turns off the 120ms fade.

THEMING: colours come only from CSS variables. Kind tokens are defined in styles.css :root (light), again under @media (prefers-color-scheme: dark) :root:not([data-theme='light']), and again under :root[data-theme='dark'], together with the new opaque --card. The campaign's gothic or pastoral setting only changes the 3D world, which never shows through a card because --card is opaque.

There are four warm kinds (condition, item, damage/dice, monster/creature type). They are always told apart by glyph and type word as well as hue. An automated check renders the chips through deuteranopia and protanopia matrices and asserts that every pair of kinds differs in glyph and type word. Then a screenshot set in scratchpad/clarity/ is reviewed. The violet DM hue is never used for a rules kind. The green and red movement and strike overlay colours exist only on the canvas, and chips exist only in DOM cards.

kinds.ts maps every lookup() kind through an exhaustive TypeScript switch ending in a never-check, so a new kind fails the build instead of rendering uncoloured.

DM-ONLY GUARDING:
- Every tip and card is built from TipSource[] = { text, audience: 'player' | 'dm', kind? }. renderTip(sources, ctx) drops every 'dm' source when app.restricted or app.mode === 'player', before any string is built. - The trigger guard (ignore triggers with a display:none ancestor, or under .dm-only, .dm-note or .lbl.key) applies only when restricted or mode === 'player'. In DM view, key-label and note tips work.
- The Player Display (?display=player) mounts no tooltip manager.
- When restricted, turn-bar chips carry no title, data-tip or tip.
